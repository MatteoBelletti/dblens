# Safety model

dblens is pointed at real databases by a language model. This page lists everything it can execute,
and what stops each of those things from doing harm.

## What never happens

- **No writes.** No tool changes the database. Proposed DDL is returned as text (`SqlFix.Kind = Ddl`)
  for a human to review.
- **No row data.** No tool returns a row value. The only numbers that come from data are counts.
- **No cloud.** The server runs locally over stdio; nothing leaves the machine except the tool
  results the MCP client asked for.

## What can execute

Three paths execute a query. All three are off by default.

| Path | Who writes the SQL | Returns |
|---|---|---|
| `explain_query` with `analyze: true` | the caller | a plan with real row counts |
| `analyze_denormalization` with `verifySignals: true` | dblens, from the catalog | two counts per probe |
| `infer_relationships` with `verifyCandidates: true` | dblens, from the catalog | two counts per probe |

### `explain_query`

1. **Statement guard** (`Analysis/QueryPlan/StatementGuard.cs`). Runs in `DatabaseInspectorBase`
   before any connection is opened, so no dialect can skip it. Accepts exactly one pure `SELECT`
   (a leading `WITH` is fine) and rejects `INSERT`, `UPDATE`, `DELETE`, `MERGE`, DDL, transaction
   control, a second statement, data-modifying CTEs, `SELECT … INTO` and `SELECT … FOR UPDATE`.
   Comments, string literals and quoted identifiers are blanked before the scan, so neither
   `-- delete` nor a column named `"delete"` changes the verdict.
2. **Always rolled back.** The statement runs inside a transaction that is never committed. On
   PostgreSQL that transaction is also `READ ONLY`, so the engine itself refuses a write. SQL Server
   has no read-only transaction, so there the guard is the load-bearing check — the result says so.

With `analyze: false` nothing executes; every row count is an estimate.

### Signal verification

Probes are generated by dblens from catalog names, never taken from the caller:

- **Aggregate only.** Each probe selects two counts — rows compared, rows diverging — and never a
  value. "1,240 of 8,300 rows disagree" is the entire content.
- **Quoted identifiers.** Every name goes through `SqlIdentifier`, so a hostile table or column name
  cannot inject SQL or a keyword.
- **Same guard as `explain_query`.** A generated probe that the guard rejects is not run.
- **One transaction per probe, always rolled back.** PostgreSQL: `READ ONLY` with a `statement_timeout`.
  SQL Server: `READ UNCOMMITTED` with a 5 s lock timeout, so a scan never blocks writers (the result
  notes that dirty reads can skew a count).
- **Bounded.** At most 20 probes per call, 10 s per probe, 30 s in total, and no table over
  5 million rows (or with an unknown row count). What is not run is reported as skipped, with the
  reason.
- **Failures don't propagate.** A probe that fails (permission, timeout, type error) leaves its
  signal unverified and adds a caveat; the rest of the analysis is still returned.

### How a measurement is reported

- A measurement promotes only the statement it measured. The title states the count, and
  `Confidence: 1.0` applies to that count; the diagnosis sits under `WHAT THIS MAY MEAN:` and is
  not certified by it — a deliberate snapshot and a stale cache give the same number.
- Zero rows compared is `Inconclusive`, never `Refuted`.
- A refuted signal is still a fact and is reported at `Info`.
- Rule IDs never change with verification; the state lives in which list a result is in, in
  `Evidence`, and in `Metadata["verification"]`.

## Results that could read as an all-clear

| Tool | Empty result means | What it reports instead |
|---|---|---|
| `scan_gdpr` | no column *name* matched | `Coverage`: columns it could not interpret, plus an explicit caveat |
| `analyze_fragmentation` | maybe nothing was measured | `StatsAvailable: false` and the reason |
| `check_migration_safety` | maybe nothing was recognized | statements of kind `Unknown` |
| `analyze_indexes` (`unused-index`) | maybe counters were just reset | uptime caveat; rule skipped under 7 days |
| `check_cascade_paths` | no *declared* cascade | disclaimer: ORM cascades and triggers are invisible |

Every tool description also says explicitly what the response does **not** contain, so the model
does not fill the gap by guessing.
